### A common contract with locally sufficient instructions

Use the same meanings and predictable locations for **Intent and applicability; Inputs and local bindings; Non-goals; Must not; Interaction and authority; Procedure; Completion and evidence**. State autonomous discretion alongside authority: the agent may select methods, investigate necessary context, perform bounded prerequisites, recover from ordinary failures and complete relevant verification within the agreed objective and permissions. These are authoring conventions, not a mandatory multi-step execution ceremony. A small alias can express its contract in a few lines and explicitly inherit its target's boundaries. Larger skills should put the selected mode and the most consequential constraints before detailed mechanics.

Define a non-goal as an outcome the skill does not select by default; an explicit user request or authorized parent workflow can select it without a redundant confirmation. A non-goal does not forbid necessary supporting work within the agreed objective. A must-not is a genuine prohibited action or claim under the active authority and constraints, not a default preference written as an absolute. For example, invoking a status report does not itself select history repair; an authorized history workflow can still use that report. In either case, it must not describe stale tracking refs as freshly observed remote state. A writing editor does not select new research by default; it must not invent a factual qualifier even when research is authorized.

Pair each boundary with the permitted autonomous behavior or unresolved outcome. Keep concise explicit non-goals/must-not sections, with specific local boundaries rather than a repeated generic list of every conceivable risk. Do not treat an unlisted step as forbidden, turn examples into exhaustive action allowlists, or add an approval gate merely because the procedure did not anticipate a routine recovery. Retain genuine effect, evidence and authority constraints. When reviewing a new prohibition, identify the concrete failure it prevents and check that it does not suppress useful initiative needed to finish the task.

Use **must** for an applicable invariant, **should** for a defeasible default with a reason, and **may** for an option. Consistent meaning is more important than replacing every existing heading. Preserve useful repetition at discovery, mode entry, and a consequential action. A shared authoring reference should prevent drift; it must not become a long glossary that every executing skill must load.

### Fabrication risks are behavior-specific

Add an evidence obligation wherever a workflow invites unsupported claims:

| Failure class | Corpus example | Required behavior |
|---|---|---|
| Invented facts or causes | clear-writing adds a workload qualifier; postmortem expects a fifth cause | Preserve the source claim; label a proposed inference and leave unknown causes unresolved. |
| Invented capabilities or guarantees | grilling specifies automated replay without an implementation | Verify the actual runtime capability; state unavailable or unverified behavior explicitly. |
| Invented authority | speculative acceptance or a diagnostic label appears authoritative | Record who actually approved which effect; a model response cannot supply human ratification. |
| Invented completion | a report template labels immediate actions completed | Default status to proposed/unknown and require observed execution evidence for completion. |
| Invented scope | a help fix becomes a product-specific README rebuild | Bind the procedure to the requested outcome and its selected mode. |

These are risk categories, not diagnoses that every affected run hallucinated. A broken jq expression is a deterministic defect; unnecessary confirmation is a control-flow defect. Neither becomes hallucination merely because it appears in the same audit. Templates, examples, scripts and UI defaults must obey the same evidence rules as prose.

### Interaction at unresolved decisions

Give each skill an explicit interaction policy describing the material decisions it needs, what existing context satisfies them, and which dependent actions wait. Consequential examples include history/ref scope, public API changes in package decomposition, privacy/publishing policy, and named-owner harness ratification. The user has affirmed these decision points alongside autonomy. Once the required decisions are settled, execution proceeds autonomously within their scope; a consequential skill does not need confirmation for every implementation choice. Ordinary prose editing, local status inspection, and bounded diagnostics can usually proceed from the request.

Prepare the concrete options and relevant evidence before the decision point. Ask once for an unresolved decision that changes scope, authority or acceptable loss; reuse a still-valid answer in composed skills. A user may explicitly choose an interactive mode even when autonomous execution is possible. If interaction is required but unavailable, preserve the pending decision and continue only independent authorized work; silence and a speculative respondent's answer never count as approval. Do not convert every skill invocation into an interview.

Routine implementation uncertainty is not automatically a material decision. Use available evidence and a reasonable bounded assumption where the consequences permit it, stating the assumption when useful. Ask when the unresolved choice would materially change the objective, authority, consequences or a decision reserved to the user. Preserve explicit interactive modes and nondelegable ratification requirements.

### Adapt local bindings before execution

Use a bounded binding step for genuinely variable terms, paths, commands and capabilities. Read the relevant local evidence, map the skill's role or concept to the project's implementation, and carry the mapping through that invocation. For example, `verification_command` can resolve to an existing project check; an execution-unit concept can map to the project's issue or tranche only if its lifecycle matches. Stable literal identifiers and protocol fields must retain their actual spelling.

Bindings have resolved, missing or conflicting outcomes. Uncertainty that affects the next action requires inspection or a focused question; irrelevant missing information need not block other work. A binding cannot silently weaken a prohibition, promote evidence into approval, rename an agent into a mechanical controller, invent an unavailable command, or change the user's objective. A semantic defect should become a proposed source correction, not an undisclosed per-run rewrite. Start with an inline convention in skills that need it; defer a new runtime adapter or general-purpose repair engine until repeated cases justify one.

### Grilling: move mechanical guarantees into gptengage in stages

Local source inspection found existing backend adapters, process timeout/cleanup, concurrent debate, idea expansion and conversation persistence. Reuse them, but do not claim they already implement the skill's graph, replay or private-rendering guarantees. Keep ordinary user grilling directly executable by the host agent. Keep interview judgment, research standards, uncertainty, minority findings, recommendations and human authority in the skill.

For O52, define a bounded first implementation instead of treating every advanced mechanism in the current skill as one build. The proposed first slice is a linear griller/respondent workflow: turn order, limits/timeouts, visible failures, saved state and private/public output separation, reusing existing gptengage invokers. The skill continues to own question quality, evidence interpretation and recommendations. Defer gradient scheduling and more elaborate graph/replay machinery until their implementation slice. This is ordinary scope selection, not a separate cost study, proof-of-failure exercise or added approval stage. Keep ordinary interviews and urgent corrections of unsupported capability claims independent of this runtime work. If a selected mode promises validated resume or replay, its required checks must exist before that promise is offered.

Move validated state transitions, revision/invalidation rules, bounded dispatch, failure accounting, checkpoint/resume, and private/public output separation into code. Begin with a bounded linear speculative workflow; qualify gradient scheduling afterward. Models can propose questions, scores and relationships; code enforces the supported structural rules. Structural validation does not prove factual accuracy or good judgment.

First repair the invocation contract: [the plugin adapter](../gptengage/src/invokers/plugin.rs#L35) silently ignores a requested model when `model_arg` is absent, and [Invoker](../gptengage/src/invokers/mod.rs#L39) returns only text. Unsupported explicit routing must be reported. Return requested model, resolved model when observable, completion status, available usage and capability provenance. Unknown identity or usage must remain unknown. Distinguish requested access, configured flags and enforced restrictions: [plugin access arguments](../gptengage/src/invokers/plugin.rs#L44) can be empty by [configuration default](../gptengage/src/plugins/mod.rs#L60), so `ReadOnly` alone does not prove sandbox enforcement. Require evidence of the selected mode's necessary restrictions before replacing direct-host execution.

A hard token cap requires an enforcement/reservation mechanism covering all concurrent and nested calls. Usage reported after completion cannot enforce a cap by itself. If that mechanism is unavailable, identify the bound as unsupported or best-effort before launch; wall-clock and node limits remain independently enforceable. Preserve the existing [gptengage invocation contract](references/gptengage-invocation.md) at the launch boundary: selected providers, authorized outbound data, access scope, cost exposure and named-session persistence disclosure. Runtime qualification cannot itself authorize new recipients, persistence or write permissions when replacing a native internal debate.

Two existing behaviors require deliberate migration: [debate](../gptengage/src/orchestrator/debate.rs#L324) drops failed participants, whereas grilling requires failed slots to remain visible; [conversation sessions](../gptengage/src/session/mod.rs#L145) replay text history, which is not deterministic workflow replay. The [current skill](skills/grilling/SKILL.md#L669) explicitly excludes gptengage for its internal debate. Amend that selected-mode boundary intentionally, preserve direct-host behavior until the replacement is qualified, and keep runtime-specific topology separate from respondent ownership of specialist reasoning. Do not ship every speculative retrieval/ranking mechanism merely because it is described in the current skill.

### Design for Astra first; qualify other models later

Astra is the initial design and evaluation target. Optimize wording, salience, useful repetition, delegation, autonomy and stopping behavior for the actual Codex Astra configuration. Establish its behavior on isolated skills and realistic compositions before broad rollout. GLM and DeepSeek checks are a later compatibility phase, not a prerequisite for the initial design or rollout.

Use Medium reasoning as the default target for the upcoming bounded fixes, documentation edits and convention pilot, reflecting the user's token-cost preference. Reserve higher reasoning for a specific unresolved architectural question or difficult failure that warrants it; the campaign does not need to remain at X High. This is a working preference, not a claim that writing this plan changes the active session's reasoning setting.

Later, run the relevant cases through the intended GLM 5.3 Flash and DeepSeek V4 Flash 0731 hosts/adapters. Record exact requested/resolved identity where available, runtime version, reasoning settings, tool permissions and loaded skill set. If a demonstrated difference requires a variant, adapt the affected instructions or execution mechanics while preserving intent, authority and evidence requirements. Prefer small targeted variants over duplicating whole corpora; do not preclude a larger variant if evaluation demonstrates it is necessary. Do not claim portability before those checks.

Model-sensitive behavior is documented: OpenAI's Astra guidance discusses instruction sensitivity, clarification, delegation and verification calibration ([official guide](https://developers.openai.com/api/docs/guides/latest-model)). DeepSeek's 0731 release evaluation specifies its harness and inference settings ([official release notes](https://api-docs.deepseek.com/updates/)). These sources support testing the complete configuration; they do not establish a ranking for this corpus. No comparative model runs were performed in this audit or follow-up.

Use the existing verification cases selectively for the changes being made, initially on Astra: a narrow edit, composed PR preparation, a missing-tool path, approval reuse/conflict, an unsupported factual claim, and ordinary versus speculative grilling. Include autonomy cases that require a sensible unlisted prerequisite or bounded recovery, and a case that must wait for a material unresolved decision where relevant. A run that avoids violations by failing to finish authorized work does not pass. Check completion, appropriate initiative, forbidden effects, unsupported claims and unnecessary stops/questions. Retain useful repetition; a line-count reduction is not evidence of improvement. Expand checking only for a failure or unresolved concern. Later model qualification is a separate phase, not a universal panel for wording fixes.

Do not require matched before/after behavior records, a baseline campaign or comparative scoring for this work. Use focused validation of the changed behavior, with disposable fixtures for harmful recipes and existing regression checks where relevant. Reproduce a defect when needed to understand or verify its fix, without turning that into a separate measurement process. Passing checks establish the properties they exercise; they do not demonstrate a quantified performance improvement.

## Concrete behavior contracts to preserve

### Authority and stopping

- Current user intent, explicit scope, and still-valid authorization carry across composed skills. Loading a child skill neither widens authority nor erases it.
- A real unresolved approval boundary stops only dependent work. Safe, useful preparation should reach a concrete result first.
- Existing nondelegable approvals remain nondelegable. Do not replace a product-owner decision, sensitive-data disclosure decision, force-push approval, or vocabulary merge approval with “the agent thinks it is routine.”
- Reuse formal approval only for the same approval-relevant brief identity, required actors, decisions, effect scope and still-valid grants. A changed prepared digest follows the controller's actual invalidation rules. Changed approvers, ambiguous owners, omitted effects, or stale evidence require the affected decision again. Draft authority is not construction/run authority.
- A heuristic warning is evidence to examine. A demonstrated breach of an active rule can stop work. The two must not share an unconditional generated instruction.
- In the reactor, stopping because an action exceeds the agreed envelope is correct. In ordinary execution, importing a reactor-specific ban is a routing defect.

- `grilling` keeps the human interview small; researched linear and lattice modes load their own mechanics. Question-only griller rules do not prevent a respondent from answering or an orchestrator from giving the explicitly selected final synthesis.

Opting into graph display only changes the visible projection. O11 moves mode-specific requirements; it does not turn correctness into an optional debug feature.
- Keep the existing division between bounded execution and epic selection. Do not make a simple code task acquire a product thesis, charter, typed DAG, harness, and durable ledger merely because all are available.

- Shared references must resolve in the source package, assembled Codex/Claude trees, and Pi's symlink layout. Keep critical constraints discoverable without requiring an unavailable sibling skill.
